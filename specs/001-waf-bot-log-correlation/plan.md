# Implementation Plan: Multi-Vendor WAF & Bot-Defense Log Correlation

**Branch**: `001-waf-bot-log-correlation` | **Date**: 2026-08-06 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-waf-bot-log-correlation/spec.md`

## Summary

Build a multi-tenant log management platform that ingests WAF and bot-defense logs from Cloudflare,
F5, and DataDome, normalizes them onto one common event model, joins the events that describe the
same client request into a single correlated record with an explicit confidence level, and exposes
search, dashboards, and webhook alerting over that correlated view.

**Technical approach**: A Go backend built on go-kratos, structured as three deployable binaries —
`siem-ingest` (vendor receivers and pull workers), `siem-processor` (normalization, correlation,
alert evaluation, retention), and `siem-api` (the OpenAPI surface the frontend consumes). Vendor
deliveries are acknowledged only after a durable commit to Redpanda, then normalized into
ClickHouse. Correlation is a windowed streaming join in Go using a ranked signal set — exact vendor
request identifiers first, then a bounded IP/host/path/method/time heuristic with degraded
confidence. The frontend is a Vue 3 + Vuetify 3 SPA whose API client is generated from the same
`openapi.yaml` the backend publishes. Everything builds through a root `Makefile` and runs locally
through Docker Compose.

## Technical Context

**Language/Version**: Go 1.24 (backend), TypeScript 5.x / Node 22 LTS (frontend)

**Primary Dependencies**: go-kratos v2 (framework, HTTP/gRPC transports, middleware, config),
`protoc-gen-openapi` (gnostic) for OpenAPI v3 generation, `buf` for proto lint/breaking checks,
`clickhouse-go` v2, `franz-go` (Redpanda/Kafka client), `go-redis` v9, Casbin v2 (RBAC with
domains), `golang-migrate` (ClickHouse driver), `golangci-lint`; Vue 3, Vuetify 3, Vite, Pinia,
vue-router, `openapi-typescript` + `openapi-fetch`

**Storage**: ClickHouse as the sole persistent store of record — event tables (`raw_events`,
`normalized_events`, `correlated_requests`, `rejected_events`), control-plane tables as
`ReplacingMergeTree`, and an append-only `audit_entries` table. Redpanda provides the durable
ingest queue; Redis holds only ephemeral state (sessions, ingest dedup window, rate-limit counters,
correlation window state) and is never a system of record. See [research.md](./research.md) R6 for
the accepted trade-off of putting control-plane data in ClickHouse.

**Testing**: `go test` (table-driven), `testcontainers-go` against real ClickHouse/Redis/Redpanda
for integration tests, fixture-replay suites per vendor adapter and for correlation, fuzzing on the
three parsers, contract tests asserting handlers match `openapi.yaml`; Vitest + Vue Test Utils and
Playwright on the frontend

**Target Platform**: Linux x86-64 containers, orchestrated locally with Docker Compose; browser
target is current Chrome, Firefox, Safari, and Edge

**Project Type**: Multi-tenant web application — Go backend services plus a Vue SPA

**Performance Goals**: 5,000 events/sec sustained combined ingest with 15,000 events/sec peaks for 5
minutes (SC-002); an ingested event searchable within 60s p95 (SC-003); first page of a 24-hour
search returned in under 3s p95 (SC-005)

**Constraints**: No acknowledged event may be lost (SC-001); ≥95% cross-vendor join rate with <1%
false joins (SC-004); every query carries a mandatory time range, a result cap, a server-side
timeout, and cursor pagination; zero cross-tenant exposure (SC-009); expired data deleted within 24h
(SC-010); log-derived content must render inert in the browser

**Scale/Scope**: Design target of 50 tenants, 3 feeds each, ~400M events/day at sustained rate;
approximately 30 API operations, 10 ClickHouse tables, 3 vendor adapters, and 12 frontend screens

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-checked after Phase 1 design.*

| Principle | Gate | Initial | Post-Design | How this design satisfies it |
|-----------|------|---------|-------------|------------------------------|
| I. Contract-First Backend & Frontend Separation | Versioned machine-readable contract committed before implementation; frontend holds no business/authz logic; generated clients only | PASS | PASS | Annotated protos generate both Kratos HTTP handlers and `backend/api/openapi.yaml` (v3, committed, `/api/v1` versioned). Frontend client is generated by `openapi-typescript`; CI fails on regeneration drift. All verdicts, correlation, retention, and authorization decisions live in `siem-api`/`siem-processor`. |
| II. Ingestion Integrity | Ack only after durable commit; stable event identity; dead-letter with reasons; raw payload preserved; explicit backpressure | PASS | PASS | Vendors are acked only after `acks=all` to Redpanda. Every event carries a `event_id` derived from the vendor's own request identifier plus feed id, making retries idempotent. Unparseable and over-quota events go to `rejected_events` with a coded reason and a counter. `raw_events` stores the byte-exact vendor payload. Over-quota returns 429 with `Retry-After`; consumer lag is the published backpressure signal. |
| III. Test-First | RED→GREEN→refactor; contract tests; fixture tests for parsers and rules; ≥80% coverage; regression test per bug | PASS | PASS | Tasks are ordered test-first. Each vendor adapter ships with a fixture corpus including malformed input; correlation is verified against a labelled replay corpus that is the only way SC-004 is measurable; contract tests diff handler behavior against `openapi.yaml`. `make test` enforces the coverage floor and blocks CI. |
| IV. Tenant Isolation & Least Privilege | Tenant scoping at the data layer; deny-by-default RBAC; boundary validation; append-only audit; no hardcoded secrets | PASS | PASS | Tenant id comes from the verified token claim and is injected via request context — repository methods expose no caller-supplied tenant parameter. Casbin RBAC-with-domains enforces Admin/Analyst/Auditor/Ingest-Only, deny-by-default, in Kratos middleware applied globally. Every request body is validated against the generated schema at the boundary. `audit_entries` is append-only `MergeTree` with no application delete path. All secrets come from env/secret manager and are checked present at startup. |
| V. Observability & Bounded Performance | Structured logs with trace id; ingest/query metrics with alerts; bounded queries; stable error codes; asserted performance targets | PASS | PASS | Kratos logging middleware emits JSON with a trace id propagated from the SPA. Prometheus metrics cover ingest rate, lag, query latency, error rate, rejected count, and storage usage, with alert rules shipped in `deploy/`. Every query API requires a time range and enforces `LIMIT` + `max_execution_time` + cursor pagination; unbounded requests are rejected with a stable error code. SC-002/003/005 are asserted by a load test in CI's nightly job. |

**Security, Compliance & Retention section**: TLS everywhere; ClickHouse at-rest encryption via
volume encryption; argon2id password hashing; per-tenant TTL-driven retention with partition-drop
deletion and an audited purge path; append-only events with no update path; per-tenant and
per-credential rate limits; `v-html` banned by lint rule plus strict CSP; dependency and secret
scanning blocking in CI.

**Development Workflow section**: Research-and-reuse performed and recorded in
[research.md](./research.md) (Kratos OpenAPI toolchain, ClickHouse ReplacingMergeTree patterns,
Casbin, golang-migrate, testcontainers — all adopted rather than hand-rolled). File-size and
function-size limits are enforced by `golangci-lint` (`funlen`, `gocognit`, `lll`) and ESLint.

**Result**: PASS. Three deviations are recorded in [Complexity Tracking](#complexity-tracking).

**Structure Decision**: Backend and frontend are separate top-level trees, matching Constitution
Principle I's two-tier split, with `backend/api/openapi.yaml` as the only interface between them.
The backend follows the Kratos layering convention (`service` → `biz` → `data`) so generated code
and hand-written use cases stay separated. Three binaries share one module and one `internal/` tree:
they have genuinely different scaling profiles (ingest is network-bound and bursty, processor is
CPU-bound and stateful, api is latency-sensitive) but no separate dependency sets, so splitting them
into separate modules would add build complexity for no isolation benefit. Vendor adapters are
siblings under `internal/vendor/` behind one interface so a fourth vendor is an added directory, not
a change to the pipeline.

## Complexity Tracking

> Deviations from the simplest design, recorded per Constitution governance.

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Redpanda as a required component (a fourth piece of infrastructure) | Constitution Principle II forbids acknowledging an event before durable commit, while ClickHouse punishes per-request inserts. A durable log is the only way to satisfy both, and it additionally provides the replay needed for FR-018 late arrivals, the dead-letter path for FR-006, and the consumer-lag backpressure signal for FR-007/FR-008. | Direct ClickHouse `async_insert` with `wait_for_async_insert=1` is durable but offers no replay, no dead-letter, and no lag signal; a ClickHouse outage would become an immediate ingest outage with nowhere to buffer acknowledged traffic. |
| Redis in addition to ClickHouse | Correlation window state, the short-window ingest dedup set that produces FR-004's duplicate count, per-tenant rate-limit counters, and refresh-token revocation are all high-churn, short-TTL, read-modify-write workloads. ClickHouse is structurally wrong for every one of them. | In-process state was rejected because it breaks as soon as a second processor or ingest replica runs, and correlation correctness would then depend on which instance received an event. |
| Control-plane data in ClickHouse `ReplacingMergeTree` rather than a relational store | The storage engine was mandated as ClickHouse. Uniqueness and transactional updates are therefore enforced in application code behind a single write path with a per-entity Redis lock, plus a nightly consistency check. | PostgreSQL for the control plane is the conventional and materially safer choice for uniqueness constraints and transactions. It was rejected only because it conflicts with the stated storage directive — the repository interfaces are kept storage-agnostic so this can be revisited without touching application logic. See [research.md](./research.md) R6. |
